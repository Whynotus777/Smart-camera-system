# T13 — M1 walking skeleton: evidence

Branch `agent/T13-integration` (from `wave0-baseline`). Box: Ubuntu, RTX 5090 (driver
580.173.02), ffmpeg 6.1.1, Python 3.11. The data disk is rotational and was shared with T14's
MEVA download throughout, so wall times are pessimistic. Status and risks: `docs/RELEASE.md`.

## What runs

```
video file (looped) ─┐                         ┌─ clipper: clip job due → atomic MP4 (remux)
RTSP camera / farm ──┴─ ingest: FrameSource → M1Pipeline(Detector → Tracker → DwellEngine)
                          └─ 1 txn: events + alerts + clip jobs + checkpoint + state ─┐
                                                                            SQLite (WAL)
                                                   web: review page/API → reviews → labels
```

| Stand-in | Interface (ARCHITECTURE §4) | Replaced by |
|---|---|---|
| `source.FileLoopSource`, `source.LiveSource` (ffmpeg CLI) | `FrameSource` | T02 |
| `stubs.BackgroundDiffDetector` | `Detector` | T03 |
| `stubs.IouTracker` | `Tracker` | T03 |
| `stubs.DwellEngine`: foot point in zone ≥ 5 s → event → alert | `JourneyEngine` | T05 |
| `evidence.FileLoopEvidence` / `SegmentEvidence` (remux, `-c copy`) | `evidence.EvidenceStore` (new, T13) | T10 |
| `web.py` (stdlib HTTP; no new dependency) | review API paths in `web.py` | T10 |
| `cli.py demo` supervisor | — | T12 |

`scs.app.pipeline.M1Pipeline` is the per-frame path. The ingest role runs it, and it satisfies
T09's `eval.e2e.StreamingPipeline`, so e2e eval scores the deployed code.

Durability design: IDs are hashes of frame identity, so re-processing is idempotent. There's one
transaction per checkpoint. File sources resume at `checkpoint + 1` with the restored
tracker/engine state. Files are written temp → fsync → rename, and the DB row follows the
rename. Each role takes a `flock` so it can't run twice, and children get `PR_SET_PDEATHSIG` so
they can't outlive their parent. The review API returns 200 only after commit and label export,
and a retry is idempotent.

## M1 acceptance

### 1. One command, headless, prints the review URL

```
$ python -m scs.app demo --video demo_1.mp4 --speed 4 --exit-when-ready
workdir: .../d1
[ingest] file source .../tests/fixtures/video/demo_1.mp4 from media frame 0 (284 frames/loop)
[ingest] event 4f94ca49 ... new
[clipper] clip 65fc18c3 [...] done
Review queue: http://127.0.0.1:18765/
```
Covered by `test_one_command_demo_prints_review_url`. `scs demo` itself needs the entry point
(handoff B2).

### 2. kill -9 → restart, 20 runs in a row

`python tests/integration/m1_chaos.py --runs 20 --seed 1000`. Each run starts ingest, clipper
and web as separate processes on a looping synthetic clip at 8× speed, with a reviewer client
posting decisions as clips become ready. It then applies two kinds of kill:

- **External SIGKILL** every 0.2–1.2 s, of a random target (ingest, clipper, web, or ingest's
  ffmpeg decoder), restarted after 0–0.5 s.
- **Self SIGKILL at crash points** (`scs.app.crash`) at each durable boundary: before and after
  the ingest commit (p = 0.5 when the commit carries events), clip attempt, before the rename,
  after the export, after "done", after the review commit, before the label rename, and before
  the HTTP response.

It stops after 3 loops (1200 frames), drains, and checks `m1_harness.check_invariants`
against an uninterrupted reference run over exactly the same frames: same events (by ID and
content), 1 alert and 1 clip per event, every due clip exists and is playable H.264 with
≥ 10 s / ≥ 5 s coverage, stored reviews == acknowledged reviews, and one valid label per review.

| Run | Commit | Result | Kills (external + crash points) | Events / clips / reviews |
|---|---|---|---|---|
| A | `6397d97` | RESULT_A | KILLS_A | ECR_A |
| B (PR head) | HEAD_SHA | RESULT_B | KILLS_B | ECR_B |

**Does the test bite? Mutation check.** Each mutant is a durability bug planted in a copy of the tree:

| Mutant | Bug | Caught |
|---|---|---|
| split | checkpoint committed in its own transaction before the events | run 0: 2 of 3 events lost. **Survived 3 runs with random kills alone**, which is why crash points exist. |
| nodecheck | a dead decoder treated as end of file | run 0: 2 events lost |
| uuid | event IDs not derived from frames (the `uuid4` default) | run 0: IDs drift from the reference |

### 3. Clip plays in a browser, ≥ 10 s before / ≥ 5 s after

- Every test run asserts codec `h264`, `yuv420p`, an MP4 container, and ≥ 10 s / ≥ 5 s coverage.
- **Browser:** Firefox 155 headless (WebDriver via geckodriver, no new dependency) loaded
  `/clips/<id>.mp4` from the review server, seeked to 12 s and played to 22.46 s: 209 frames
  decoded, 640×360, 26.25 s. Then it clicked **Confirm** on the review page, and the stored
  review and exported label followed.
- The Chrome extension's browser couldn't play *any* media, including a stock VP9 WebM from
  `python -m http.server`, so it isn't used as evidence.
- The first event after a cold start can't have 10 s of pre-roll when it fires sooner than that
  (demo_1: at 5 s). Footage from before the camera started doesn't exist. The checker treats
  "before start" like any other outage; every later event gets the full window.

### 4. Review outcome stored and exported as canonical labels

`labels/scs_review/converted/labels/<clip_id>.json`. From the browser run:
```json
{"clip_id": "d2441545…", "camera_profile": "unknown", "fps": 20.0, "label_source": "human",
 "events": [{"type": "zone_enter", "t_start": 6.05, "t_end": 11.05, "track_id": 2,
             "actor_id": null, "visible": "observed", "label_source": "human", "event_id": "324ae6f2…"}],
 "supports": {"events": true}, "extra": {"review": {"decision": "confirmed", "reason": "m1-browser-check", …}}}
```
(`t_start` 6.05 s is when the box enters the zone; `t_end` 11.05 s is when the 5 s dwell fires.)
Validated with T09's `eval.canonical.ClipLabels` in the combined tree. A dismissal exports
`events: []` (B3).

## Bugs the integration tests found in my own code (all fixed)

1. A dead ffmpeg decoder looked like end of file, so frames were skipped and events lost after a
   restart (mutant *nodecheck*).
2. Restart livelock under NVDEC: the background model spawned 25 ffmpeg processes (~25 s),
   longer than the time between kills, so ingest never came up. Now one decode pass
   (0.1 s demo_1, 2.7 s for a 5-min MEVA clip).
3. The probe cache was written non-atomically: a torn file crash-loops every restart.
4. Review POST latency grew with the queue (every POST re-exported and fsynced every label):
   up to 4.6 s. Now per-alert, 0.14–0.3 s typical on this HDD.
5. `--rtsp-env` resolved the URL into `config.json`, i.e. a credential on disk. Now `env:NAME`.
6. Labels used `visible: {cam: …}`, which T09's `ClipLabels` rejects.
7. Unpaced replay never fired a dwell (B1). The engine now measures on `source_ts ?? ts`.
8. Live evidence segments were never pruned (~1.4 GB/h per camera). Now a 120 s window that
   keeps footage pending clips need.

## Known gaps

The stand-ins are deliberately dumb (detection quality is out of scope). There's no auth on
the review page. Clips are never deleted. HEVC clips won't play in browsers (R4). SQLite
scaling to 10 cameras is unmeasured (R12). The live wall-clock mapping of segments is
approximate (R10).
